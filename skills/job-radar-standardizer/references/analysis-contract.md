# 岗位统一技能雷达分析契约

契约版本：`radar-policy-v1-design`。这是待接入应用的设计规范；当前版本号不表示生产功能已启用。

本契约是岗位指标生成、候选人证据提取、程序评分、缓存和 AI 复核的共同依据。产品实施说明见仓库 `docs/job-radar-standardization.md`。应用需实现字段校验、持久化与计算，不能只把本文件发给模型就声称完成规范化。

## 1. 固定边界

- 同一个岗位画像版本使用同一组维度 ID、含义、顺序、权重与等级锚点。
- 岗位画像只由岗位材料及版本化职业模板产生。候选人简历、旧候选人分数和排名不参与画像生成。
- 默认等权；优先保留 5–6 个相关维度，最多 8 个。相关性优先于凑数；只有 1–2 个可靠维度时显示明细与资料不足说明，不补造多边形。
- HR 已提供的技能/要求保留其事实含义；去重和概念合并保存来源对应关系。AI 推定项显示来源，不能自动成为红线或 HR 已核实事实。
- 雷达、证据明细和岗位证据分引用同一评估快照。综合参考匹配、红线、加分项和真实性风险各自留有依据，不回写雷达等级或权重。
- 规范化规则、模板、提示词、模型配置和评分算法均有版本。已成功评估保留其实际使用版本。

## 2. 输入与不可变记录

### 2.1 岗位来源快照

必要输入：岗位 ID、岗位名称、已有技能、核心能力、岗位职责/JD、资料来源。行业、部门、职级、业务场景等仅使用实际提供的值。

`job_source_hash` 对影响岗位含义的字段做规范化序列化后计算。保留 UTF-8 文本完整性；截取长文本采用字符/段落边界，并记录截取范围，不使用可能破坏字符的字节切片。岗位名称/JD/技能发生实际文本变更时重新计算来源键；旧画像继续存在，新来源进入新画像版本流程。

规范化可统一换行及尾随空白；不应删除技术版本号、否定词、日期或改变技能要求含义。字段和数组顺序的处理规则必须版本化，不能随调用变化。

### 2.2 固定岗位画像 `JobRadarProfile`

```json
{
  "profile_id": "job_radar_123",
  "profile_version": 1,
  "profile_hash": "computed-by-application",
  "job_source_hash": "computed-by-application",
  "policy_version": "radar-policy-v1",
  "template_id": "qa-automation",
  "template_version": 1,
  "origin": "ai_inferred",
  "status": "active",
  "assessment_date": "2026-10-20",
  "dimensions": [
    {
      "dimension_id": "test-case-design",
      "name": "测试用例设计",
      "order": 1,
      "weight": 1,
      "source_refs": ["job_description:paragraph-2", "template:qa-automation@1"],
      "anchors": {
        "0": "有明确、可核对的未达到最低锚点信息",
        "1": "原文说明了解或学习过测试用例设计",
        "2": "在具体项目中参与编写并执行测试用例",
        "3": "独立设计测试覆盖方案并交付用例与缺陷闭环",
        "4": "主导复杂业务测试策略，能说明覆盖取舍及交付效果"
      }
    }
  ]
}
```

示例仅展示单个维度的字段，不代表实际画像只需要一个维度。权重是固定正整数；默认每项为 1，不由候选人材料决定。

应用分配和校验稳定 ID，AI 可以提出候选概念名称，但不能在每份简历中重新命名 ID。名称或别名变化与概念变化应有明确映射记录；无法确认同一含义时建立新画像版本，不采用子串包含作为身份映射。

### 2.3 简历来源快照

每份简历/附件记录 `document_id`、原始文件摘要、提取文本摘要、提取器版本、规范化版本、来源类型，以及固定的规范化文本。多来源的顺序与主次关系进入输入清单；附件、解析器或文本变化产生新输入键。

`assessment_date` 固定在岗位评估上下文中，参与输入键。工作年限等时间计算以该日期为准；重叠工作区间按规则去重，不能用多段年月相加制造额外经验。新日期评估建立新上下文，不能让历史结果随今天的日期自动漂移。

## 3. 空技能时如何生成指标

1. 读取岗位快照，提取岗位工作目标、主要任务、技能、工具及业务场景。保留显式要求，识别重叠概念。
2. 对完整岗位材料：AI 提出相关维度与逐级锚点；每项关联岗位原句或明确的模板依据。不要把所有 JD 条目提升为硬性门槛。
3. 对仅有标题的岗位：优先使用已维护模板及其锚点，必要时 AI 只做受约束的模板选择/措辞适配；显示 `ai_inferred` 或 `template_inferred`、模板版本和资料缺口。模板是产品维护资料，不自动宣称为法定/行业权威标准。
4. 对混合或歧义岗位：结合真实 JD 区分职业语义。例如测试开发与通用后端开发不能只按“开发”二字匹配。无可靠匹配时继续整理候选人原文，画像标记待完善，正式排名暂不可用。
5. 校验数量上限、空项、概念重叠、来源相关性、固定顺序、完整锚点与正整数权重。不得使用模糊泛化的“综合素质”补齐技能数量。
6. 在岗位级创建保护下提交一套画像，保存成功后分发给候选人。相同来源版本的并发请求返回相同活动画像。

优先级：HR 明确事实 → 完整 JD 中的工作任务 → 适用的版本化职业模板 → 标注不确定性。模板/模型失败时返回明确状态，不伪造成功画像，也不让前端自行补轴。

## 4. 逐维证据与等级

### 4.1 证据状态

| 状态 | 含义 | 等级 |
| --- | --- | --- |
| `known` | 原文可定位，且能支持至少一个明确锚点，包括明确的低等级或否定信息。 | 整数 0–4。 |
| `unknown` | 没有足够的原文信息，或所给引用不能支持该维度。 | `null`。 |
| `conflict` | 多段信息互相矛盾，无法按现有材料确定等级。 | `null`，保留冲突引用。 |

缺少技能关键词、旧版本未评估、引用定位失败，均不能直接变成已知 0 级。0 级需要明确可核对的信息；简历没写不等于不会。

### 4.2 通用等级语义

| 等级 | 通用含义 | 依据方向 |
| --- | --- | --- |
| 0 | 明确未达到最低锚点 | 明确的否定陈述或已记录的 HR 核实信息；不得由沉默推断。 |
| 1 | 了解/存在相关线索 | 原文提及学习、熟悉或了解，但缺少具体承担任务。 |
| 2 | 参与 | 有具体项目或工作任务，能定位本人参与内容。 |
| 3 | 独立完成 | 有独立职责、交付范围与结果，满足该维度固定锚点。 |
| 4 | 主导并可复盘 | 有复杂场景下的主导职责、关键决策或取舍，以及可核对的交付效果。 |

具体岗位的锚点在画像创建时确定。不能每次分析依据候选人的强弱重新解释“独立”或“主导”。量化数字有助于说明结果，但不是所有岗位达到高等级的必需形式；按该画像已定义的证据条件判定。

应用取“证据充分支持的最高锚点”。模型的自报置信度不直接换算为等级，也不参与权重。若语义支持仍不明确，保留未知或较低的已支持锚点，并说明缺失信息。

### 4.3 原文引用

每条证据包含来源 `document_id`、原文引用、规范化文本位置及支持的锚点条件。位置使用固定规范化文本的 Unicode 码点下标，区间为 `[start, end)`；应用核对实际片段等于引用。

如模型不能可靠提供位置，可由应用进行精确文本定位；出现多个相同片段时保留各候选位置并要求消歧，不通过跨段拼接或删改文字制造引用。引用与文档快照一致，只证明该主张在原文出现；HR 核实记录应另存。

一段经历可在语义上支持多个维度，但每个维度都要说明各自支持关系。不能把同一条旧技能以模糊名称批量映射到不同指标；同维度重复引用不重复加分。

### 4.4 模型输出与应用职责

模型返回证据建议，不返回权威总分：

```json
{
  "profile_hash": "echo-input-profile-hash",
  "dimensions": [
    {
      "dimension_id": "test-case-design",
      "evidence_status": "known",
      "proposed_level": 2,
      "evidence": [
        {
          "document_id": "resume_text_1",
          "quote": "参与订单系统测试用例编写与执行",
          "start": 120,
          "end": 137,
          "supports": ["concrete_project", "participated_task"]
        }
      ],
      "missing_information": ["是否独立负责完整测试覆盖方案"]
    }
  ]
}
```

示例位置是字段形态展示，实际请求必须针对真实快照核对，不可复制示例位置。正式契约中每个画像维度都要出现且仅出现一次；未知项明确返回状态及 `null`。

应用检查画像哈希、ID 集合、重复项、状态/等级一致性、引用及锚点支持字段。应用可确定性地做语法修复；语义缺失时最多进行一次面向缺失字段/维度的修复请求，并保留调用记录。不要多次抽样后挑选得分最高或最接近旧分数的回答。

引用验证和规则计算不能完全替代语义判断。新的模型推理可能对同一引用作出不同解读；持久化证据建议、人工复核和独立回归测试用于处理这部分不确定性。

## 5. 程序评分与 80% 排名门槛

定义：每个维度固定权重 `w_i > 0`；已知集合 `K` 只包含 `known`，等级 `l_i ∈ {0,1,2,3,4}`。`unknown`、`conflict` 不进入已知集合。

```text
W_all   = Σ全部维度 w_i
W_known = Σ已知维度 w_i
P_known = Σ已知维度 (w_i × l_i)

coverage = W_known / W_all
known_score = 100 × P_known / (4 × W_known)       # W_known=0 时为 null
lower_bound = 100 × P_known / (4 × W_all)
upper_bound = lower_bound + 100 × (W_all-W_known) / W_all

rank_eligible = 输入与画像有效 且 W_known×100 >= W_all×80
official_score = known_score（rank_eligible=true 时），否则 null
```

上下界表示未知维度可能为 0–4 时的全维度得分范围，不是概率或统计置信区间。已知项归一化会让不同缺项分布的人存在可比性局限；按用户选择，达到 80% 后仍允许排名，界面同时展示覆盖率、未知轴与上下界。

计算使用整数权重/等级和有理数，最终结果只舍入一次。推荐保存 `score_bp`（0–10000，1 个单位代表 0.01 分），用四舍五入到百分之一分生成；排名门槛用未舍入权重判断，不能把 79.995% 的显示 80% 当作达标。

图和明细必须展示同一批维度；未知轴使用空缺、虚线或独立标记，不能将其填成候选人实际 0 级。正式排序限定在相同画像与评分口径；同分排序使用预先固定的次序及稳定 ID，避免页面刷新换序。已确认加分项可以作为单独、明示的排序辅助，但不能改变雷达等级或岗位证据分。

### 评分夹具

| 权重与等级 | 覆盖率 | 已知项分 | 正式排名 | 全维度区间 |
| --- | --- | --- | --- | --- |
| 6 项等权，`[3,3,2,4,3,null]` | 5/6 ≈ 83.33% | 75.00 | 是 | 62.50–79.17 |
| 5 项等权，`[3,2,1,null,null]` | 60% | 50.00 | 否 | 30.00–70.00 |
| 权重 `[4,3,2,1]`，等级 `[3,2,null,1]` | 80% | 59.38 | 是 | 47.50–67.50 |
| 5 项等权，`[0,3,3,2,2]`，0 有明确依据 | 100% | 50.00 | 是 | 50.00–50.00 |
| 全部未知 | 0% | `null` | 否 | 0.00–100.00 |

## 6. 相同输入的稳定性

### 6.1 完整输入键

```text
analysis_key = SHA256(canonical_json({
  source_document_manifest,
  extracted_text_hashes,
  normalizer_version,
  profile_hash,
  assessment_date,
  extractor_version,
  scoring_rule_version,
  policy_hash,
  model_profile_version,
  hr_evidence_overrides_hash
}))
```

`model_profile_version` 记录提供商/端点配置标识、具体模型和推理参数版本，不包含 API Key。请求 ID、重试次数、界面状态、完成时间不进入键。模型配置切换不自动改写旧评估；新管线需校准后才能与已有口径混排。

缓存命中时读取成功证据快照并用同版规则复算；无需模型调用。材料、指标、规则、基准日期或 HR 证据修正变化时得到新键，保留父记录。

### 6.2 并发和失败

- 相同岗位来源版本的画像创建实行单次提交；相同输入键的评估实行幂等任务/成功记录约束。进程内锁与数据库唯一约束、事务配合使用。
- `pending → running → completed / failed / interrupted` 状态记录实际结果。错误、结构不合格或引用失败时，不将未经验证的新结果标记为成功。
- 持久化成功后才对外返回成功版本。失败重试继续固定输入快照；发现同键成功结果时复用。
- 旧成功基准不因失败重试、页面刷新或新草稿失败而清空。引用位置、字段、评分输入与计算结果一起保存，以便精确复现。

低温度和提供商支持的固定推理参数可以纳入管线配置，但不构成跨提供商或模型更新后的确定性保证。

## 7. AI 复核与更新

移除单条、批量和详情中的“重新分析”入口。后台幂等复用是内部机制，不需要新增一个同名按钮。保留首次/未完成任务的失败重试，以及人工 AI 复核。

AI 复核沿用固定画像、来源文本和基准日期，绕过成功结果复用，生成独立候选快照。提取阶段不提供“接近旧分数”的要求，不做总分限幅。

差异包含：逐维证据状态、引用、等级、覆盖率、正式排名资格和程序分数。任何复核草稿都先由 HR 查看并确认后激活；旧基准、草稿和确认记录均保留。

- 相同已知集合、相同画像/规则下，正式分差绝对值大于 3.00 分，标记显著变化。
- 任一维度双方都是已知且相差至少 2 级，标记显著变化。
- 已知/未知状态变化、覆盖率跨越 80% 或画像/输入变化，作为单独的结构变化展示。已知集合不同的总分不能直接解释为纯能力升降。
- 显著变化必须解释支持变更的原文、锚点应用或纠错原因；“模型这次不同”不能作为自动替换依据。相同原文的新解读可提出，但应明确属于解释变化而非新增事实。

新增附件/材料使用新来源版本；修改岗位使用新画像版本。它们不属于相同输入的重新分析，不应暗中覆盖旧评估。

## 8. Skill 与应用运行时的接入约束

本契约由仓库专用 Skill 引用，供开发/分析代理使用。应用在后续开发中需要打包受版本控制的规则资源，分阶段加载：岗位生成只接收岗位规则，证据提取只接收固定画像与证据规则，评分在程序中执行。

每次分析记录实际策略摘要，构建/启动检查声明版本与打包资源一致；不能仅安装 Codex Skill 就宣称应用已使用新规则。模型返回内容只按数据 schema 处理，简历中夹带的指令不改变指标、规则或允许操作。

契约、画像 schema、程序校验和测试发生变化时一并更新版本。历史数据没有版本或原文定位信息时，标记旧口径并保留原结果；不要用当前指标补零伪装完成迁移。

## 9. 完成与拒绝条件

一份可被接受的画像：来源可追溯、维度唯一且相关、规则/模板版本齐全、锚点完整、权重/顺序固定，并已可靠保存。

一份可被接受的评估：维度集合与画像完全一致、未知状态明确、所有被接受引用可定位、等级符合已支持锚点，且分数、覆盖率与排名资格可由同一快照程序复算。

资料不足、模型错误、歧义模板或引用无效时返回具体缺口与下一步；不补造技能、不伪造零分或总分、不通过截分掩盖漂移。完成声明必须区分文档规范、已实现机制与实测结果。
