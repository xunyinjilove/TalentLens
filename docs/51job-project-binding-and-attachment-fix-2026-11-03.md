# 51job 职位串库与附件简历修复记录

## 问题原因

1. 人才管理弹窗曾用职位名称的共同前缀猜选职位。“区域销售经理 宁波”和成都等同名前缀职位会碰撞；随后职位选择还可能把本地分库切到该职位以前的映射。
2. 旧数据里，宁波分库有 9 条人才库关联来自其他 51job 职位 ID。对应投递记录后来已指向其他项目，原有归档逻辑只查投递记录当前的项目，因此没有清理这 9 条遗留关联。删除本地简历后，同步可重新导入，进一步显露了错绑问题。
3. 打招呼入口没有读取项目保存的职位 ID，而是每次弹出职位选择器。
4. 附件抓取原来只认聊天消息中的直接文件链接；51job 的“附件简历”卡片可能没有直链。已有在线或附件简历时，“检查回复”还会进入只读文字分支，因而没有下载新文件。

## 已实施

- 项目只使用已保存的 51job 账号与精确职位 ID。读取职位、人才管理同步和打招呼共用该绑定；相同名称不再用前缀匹配。绑定缺失或失效时显式选择一次，冲突职位不会被静默改绑。
- 新版本启动时，按投递记录的真实账号与职位 ID 审核项目人才库关联，归档错职关联并保留记录。删除的正确职位简历仍允许以后重新同步。
- 已移除“索要简历”入口和发送索要消息的动作。“检查回复”改为只读的“同步附件简历”；单人点击立即检查已收到的附件。
- 人才管理同步结束后，独立后台任务逐人检查当前分库中身份可核验、尚无附件或待获取的 51job 人选。任务显示进度并可中止；已完成文件保留，未完成者下次续查。即使人才管理详情没有附件标记，也会检查会话卡片。
- 有直链时下载真实文件；没有直链时打开平台“附件简历”卡片并捕获平台响应或下载。无聊天或只有在线简历时记录“未发现附件”，保留在线简历，不发送消息。
- 用文件 SHA-256 去重；不同文件作为新版本，旧文件与来源历史保留，当前版本更新后重新分析。

## 验证

- Go 全量测试、前端 TypeScript 检查、51job 沟通脚本 31 项测试通过；Windows AMD64 构建与压缩包生成通过。
- 使用隔离测试目录和已登录的 51job 会话读取张健已发送的附件卡片，获得真实 PDF，提取出正文；再次抓取识别为相同文件并跳过。测试未修改正式档案。
- 宁波历史错职关联在首次启动新版本时归档。启动后核对宁波分库人数和归档记录。
