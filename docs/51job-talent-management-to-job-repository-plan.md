# 51job 人才管理按职位导入 TalentLens 专属分库方案

- 日期：2026-10-21。
- 交付范围：方案与代码改动分析；本次未执行导入，也未改动应用功能。
- 平台入口：[51job 人才管理](https://ehire.51job.com/Revision/talent/management?rt=1792570683108)。`rt` 为页面参数，不作为职位或候选人身份。
- 关联设计：[51job 公司人才库附件接入](hr-first-interview-screening-outreach-plan.md#8-51job-公司人才库与-talentlens-接入方案)。人才管理的职位和处理状态是本方案新增的导入边界，附件保存与版本规则沿用关联设计。

## 1. 目标与首版范围

HR 在 TalentLens 的某个“各职位专属分库”中，选择该分库对应的 51job 人才管理职位，再勾选要导入的处理状态：**待处理、合适、待定、面试**。软件预览匹配人选和读取范围；HR 确认后，批量把这些人选及账号可取得的简历材料导入当前分库。下次导入同一职位可复用已确认的职位映射。

“一键导入”指确认本批范围后自动逐人处理，不要求 HR 为每人重复指定职位。首次建立映射、范围不明确、登录失效或身份冲突时仍要让 HR 核对，不能猜测。

首版只从 51job 读取并写入 TalentLens 本地库。导入不会在 51job 上修改处理状态、移动简历、发送消息或邀请面试；也不自动调用 AI 分析。导入后的候选人显示为待分析，由 HR 选择单条或批量手动分析。

## 2. 核对到的现状及边界

2026-10-21 对已登录的 51job 专用浏览器进行了只读检查：当前 `/Revision/talent/management` 页面有“待处理、合适、面试、待定”筛选标签，也有按姓名或人才 ID 搜索的输入框。**这只能证明当前页面有这些可见控件**；职位筛选的稳定 ID、分页、候选人身份、完整简历与附件获取方式仍需小样本实测。51job 的[历史官方帮助](https://ehire.51job.com/help/shoujianxiang.htm)说明过按职位和招聘流程筛选，但不能替代新版页面验证。

TalentLens 当前已有：

| 位置 | 可以复用 | 不能直接套用的地方 |
| --- | --- | --- |
| `TalentPoolView.vue` | 左侧职位分库导航、当前分库候选人列表及“导入与核对”菜单。 | 现有“导入 51job 投递”没有选择平台职位和四种人才管理状态的预览流程。 |
| `platform_job_mappings`、`SetPlatformJobMapping` | 按平台、账号、平台职位 ID 关联本地项目。 | 必须核实账号作用域，不能仅按职位名称关联，也不能复用空账号的跨企业映射。 |
| `candidates`、`candidate_sources`、`project_candidates` | 同一人可有多个来源和多个岗位关联，分库按 `project_id` 读取。 | 同一候选人在 51job 的每个职位和处理状态需要独立来源记录；平台状态不能覆盖本地招聘阶段。 |
| `resume_versions`、`project_candidate_resumes` | 可保存材料版本并关联到岗位人选。 | 附件仍需单独身份、文件校验与版本记录；列表摘要不能冒充完整简历。 |
| `ImportApplications`、`scripts/51job_application_import.js` | 已登录浏览器连接、批次统计和主动投递导入经验。 | 当前适配器按投递页结构和申请 ID 读取，`queueImportedAnalysis` 还会自动分析；人才管理入口需独立适配和无 AI 的导入路径。 |

“职位专属分库”在本地是**招聘项目与候选人的关联**，并非独立复制一份人员档案。同一候选人关联两个项目时，各项目的测评和本地跟进阶段分别保存。

## 3. HR 操作流程

### 3.1 从当前分库导入

1. HR 打开“简历人才库”，在左侧选定一个职位专属分库，点击 **导入与核对 → 从 51job 人才管理导入**。也允许从“职位管理”进入同一流程并预选当前项目。
2. 软件连接当前 51job 专用浏览器，展示企业/账号作用域、上次确认的对应平台职位及映射时间。首次使用时读取平台职位列表，让 HR 选择明确的职位 ID；只有名称相似时仅做建议，不自动映射。
3. HR 勾选“待处理、合适、待定、面试”中的任意组合。界面显示每类在平台可见的人数，并注明该数值是当前筛选条件下的页面计数还是已遍历的总数。
4. 点击“读取名单”。软件遍历该平台职位与选中状态下的全部可访问页面，显示**已读取页数、已读取人选、可核验身份人数、资料待补全人数**。分页没有读完时不能称为“全部”。
5. 预览名单。默认勾选当前筛选结果，HR 可取消个别人选；“全选”明确指当前页还是本批已读取的全部人选。预览表至少显示姓名/称呼、平台人才 ID、来源职位、平台状态、简历/附件可用性、是否已在本地分库。
6. 确认页列出：51job 企业与职位、本地目标分库、所选状态、已读取范围、勾选人数、预计新增/已存在/待核对人数及附件数。HR 确认后才开始导入。
7. 导入结果按“新入库、已有记录补充、重复跳过、资料待补全、身份待核对、失败”分别统计，并保留逐人原因。打开当前分库即可看到成功人选及其 **51job 来源状态**；分析仍由 HR 手动启动。

### 3.2 从平台职位开始

从全局“导入与核对”进入时，先选择 51job 职位，再依据已保存的 `platform_job_mappings` 预选本地分库。找不到映射或同名分库不止一个时，由 HR 指定一次并保存 `(平台, 企业/账号作用域, 平台职位 ID) → 本地项目 ID`。不创建名称相同的第二个分库。

## 4. 职位和状态如何对应

| 51job 信息 | TalentLens 处理 |
| --- | --- |
| 平台职位 ID 与企业/账号作用域 | 通过明确映射找到唯一 `project_id`；显示职位名称只供核对。平台职位变更或账号切换后，旧映射不可跨作用域使用。 |
| 待处理、合适、待定、面试 | 作为**平台处理状态快照**保存，并在分库中作为可筛选标签展示。可保留原始平台文字与读取时间。 |
| 本地 `project_candidates.stage` | 新导入人选默认按本地入库/待分析流程建立；再次导入不得重置 HR 已有的“沟通中、初面、暂缓”等阶段。 |
| 平台“面试” | 不自动新建本地面试日程，也不宣称已通知候选人。只有实际取得时间、方式和面试对象并经 HR 确认后，才写入 `interviews`。 |
| 平台职位与本地岗位要求 | 导入只确定归属；不把平台状态“合适”视为 TalentLens 测评通过，也不复制其他岗位分数。 |

建议在分库筛选区增加“51job 处理状态”筛选，并与现有“本地招聘阶段”“分析状态”分开显示。51job 状态后续变化时，重新导入更新来源快照和状态历史，不篡改本地 HR 记录。

## 5. 身份、材料与重复导入

1. 候选人优先用 `(平台, 企业/账号作用域, 稳定平台候选人 ID)` 匹配 `candidate_sources`。如页面只有稳定申请/人才管理记录 ID，可先用该 ID 识别职位下来源记录；是否能跨职位归并为同一人需另核对。姓名、列表行号、职位名称及 `rt` 参数均不能作唯一键。
2. 建议新增 `platform_talent_management_records`：`platform`、`account_scope`、`platform_record_id`、`platform_job_id`、`candidate_id`、`project_id`、`platform_status`、`status_seen_at`、`profile_url`、`first_imported_at`、`last_seen_at`；唯一键至少覆盖平台、作用域和稳定来源记录 ID。若一个来源记录 ID 只在职位内唯一，还须纳入平台职位 ID。
3. 同一人同一分库只有一个 `project_candidates` 关联；重复导入只更新来源状态和新增材料。不同职位保持不同项目关联，测评和跟进互不串联。同名而无稳定身份的条目进入“身份待核对”，不得自动合并。
4. 完整简历文本与附件分别标记获取状态。附件下载后按内容 SHA-256 去重，新内容成为新版本并保留旧版；失败或没有附件时保留候选人基本资料，标记“资料待补全”。附件选择、预览和版本规则沿用公司人才库方案。
5. 导入任务保存选定的职位 ID、状态集合、稳定候选人/来源记录 ID、读取时间、分页进度和逐人结果。暂停或登录过期后仅继续未完成项；对回执不明的文件下载先核对本地是否已保存，再重试。

## 6. 服务和界面改动

```text
51job 已登录人才管理页
    → 只读页面适配器：职位、状态、分页、名单、详情/附件描述
    → 预览与 HR 确认：平台职位 ID、四种状态、名单范围、目标分库
    → 可恢复的导入批次
    → 统一候选人和来源记录 → 项目候选人关联 → 材料版本
    → 当前职位专属分库：来源状态、资料状态、手动分析入口
```

建议新增 `scripts/51job_talent_management_import.js`，与主动投递适配器分开。适配器只接受当前账号已登录的 51job 页面，读取平台真实字段并输出明确的分页完整性；不得通过未证实的 DOM 类名或模拟状态修改接口“凑齐”记录。

后端新增预览、创建批次、查询进度、继续失败项与来源状态查询接口。导入服务复用统一候选人/项目关系，但不要调用 `ingestApplicationRecords` 的自动分析路径或 `queueImportedAnalysis`。批次与逐人写入应具备幂等约束；外部详情读取和附件下载在事务外执行，完成校验后再提交本地记录。

前端在 `TalentPoolView.vue` 的“导入与核对”增加独立入口与向导。当前分库启动时锁定目标项目；如果 HR 在预览期间切换了分库、平台职位或账号，确认按钮失效并要求重新核对范围。结果面板支持“只重试失败项”和跳转到新入库人选。

## 7. 实施顺序与验收

| 阶段 | 工作 | 验收标准 |
| --- | --- | --- |
| A 页面实测 | 小样本验证职位 ID、四种状态标签、分页、稳定身份、详情和附件；观察查看详情是否改变平台已读状态。 | 形成字段证据；无法证明的字段保持未验证，不启动批量导入。 |
| B 预览与映射 | 当前分库预选职位、状态多选、遍历页数、名单勾选和确认摘要。 | 账号或职位不符时阻止导入；无映射时只需 HR 指定一次。 |
| C 导入与恢复 | 身份去重、来源状态、项目关联、材料版本、进度与重试。 | 重复执行不增加同人同岗关联；中断后继续未完成项；导入 AI 调用数为 0。 |
| D 分库呈现 | 展示平台状态与资料状态、来源筛选、手动分析入口。 | 平台“面试”不产生虚假日程；本地阶段和旧测评不被覆盖。 |

至少覆盖以下验收样例：四种状态分别导入与组合导入；两页以上的结果；同一人状态从“待处理”变成“合适”；同名不同 ID；同一平台候选人对应两个职位；平台职位 ID 与目标分库不符；缺少稳定身份；附件部分失败；登录失效后恢复；重复点击确认。每个样例核对本地新增数、重复数、资料状态、项目归属及平台无状态写入。

## 8. 尚待平台验证的关键问题

当前已确认页面有四种状态入口，尚未验证下面这些实现前提：

- 当前职位筛选控件是否给出可稳定读取的平台职位 ID；列表行能否证明它确实属于所选职位。
- 状态计数是全部页还是当前时间筛选范围；“面试”是否还有子状态或历史面试记录。
- 列表是分页、无限滚动还是服务端搜索；读取全部匹配人选是否有可确认的结束条件。
- 人才 ID、候选人 ID、申请 ID 是否不同；同一人跨职位时哪个键稳定。
- 详情页是否会改变已读或处理状态；附件是否可下载、是否需要额外权限或点数。
- 不同 51job 操作员登录同一企业时，映射与来源记录应以企业还是操作员为隔离单位。

这些问题在阶段 A 用少量真实记录核实后再固化适配器。若页面不允许可靠地取得某项信息，软件应明确提示该批无法保证完整或需人工核对，不把列表摘要、同名候选人或未读完的页面当作成功导入。
