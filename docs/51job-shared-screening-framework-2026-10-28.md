# 51job 人才管理与人才望远镜共用筛选框架

状态：需求框架已由 HR 确认；本文是实施契约，不代表功能已经上线。  
日期：2026-10-28

## 目标和边界

- 项目是条件的唯一归属。一个项目绑定的 51job 职位及人才望远镜扫描使用同一版已保存条件；平台职位要求与项目条件冲突时，运行前提示，判定仍以项目条件为准。
- 只处理平台「待处理」及尚未有平台操作记录的人选。平台「合适、面试、待定」不参与新扫描、入库判定或旧库重筛。
- 所有启用条件均须通过才算「合格」；有确凿不符项则「不合格」；资料缺失或无法确认则「待核实」。每人展示逐项证据和条件版本。
- 扫描与平台操作分离。扫描只生成名单；HR 看过人数、原因、预计点数和消息后，分别执行「不感兴趣」或「Hi聊」。
- 本地专属分库只接收确认后的合格人选。人才望远镜的人选须首次 Hi聊成功后才入正式库；项目文案发送失败只重试文案。

## 端到端流程

```text
51job 职位/人才望远镜页面
  → 核验企业账号、职位 ID、候选人 ID、平台状态
  → 读取列表；缺少判定字段时读取详情
  → 使用项目条件快照逐项判定
  → 合格 / 不合格 / 待核实名单及原因预览
  → HR 分别确认平台操作
  → 逐人执行、核验回执、记录失败和待重试
  → 同步正式库或待处理区
```

### 职位连接

职位目录读取必须区分浏览器未连接、未登录、页面未就绪、组件结构改变、无职位、读取超时。失败时清空本轮目录及可执行状态，不允许沿用旧职位执行。只有新读取的账号与职位 ID 经核验后才能绑定项目。打开 51job 浏览器、重新读取和错误原因应在同一处显示。

### 共用条件与判定

项目条件在现有 `talent_management_strict_criteria` 上扩展活跃度：`不限、近 3 天、近 7 天、近 30 天`，默认近 7 天。条件保存后生成版本号；扫描批次保存条件快照。现有学历、年限、年龄、期望薪资、性别、求职状态、专业关键词和城市意向中，只有启用的字段参与判定。

判定顺序不应影响最终结果：逐项收集「通过、明确不符、未知」及证据；任一明确不符项使结果为不合格，否则任一未知项使结果为待核实，否则合格。列表字段不足时先读取详情。详情仍不足、附件不可访问、活跃时间不可验证，均留在待核实，不进入正式库，也不触发平台操作。待核实人选支持单人和整批补资料、重读详情及重新判定。

### 人才管理

只扫描「待处理」状态。预览先显示三类名单；HR 确认后，合格者进入对应专属分库，不合格者由独立按钮批量标记「不感兴趣」，待核实者留在待核实列表。每个人的身份、判定、动作、平台回执和失败原因单独保存，单人失败不抹去同批成功结果。

提供一次性旧库重筛。排除平台已推进的人；旧库不合格者从正式列表移到待处理区，保留恢复和审计所需数据。任何追溯性平台操作仍需 HR 查看名单并确认。条件更新后重评未处理与待核实者，并提示正式库中可能受影响的人；不重复已执行的平台动作。

### 人才望远镜

新建专用平台适配器；候选人来源是当日新出现及此前未处理的人。每项目单独设置 HR 自选的定时运行时间，并提供「立即运行当前项目」。应用关闭或电脑关机导致错过计划时，下次启动补跑；同项目同日手动与定时结果合并，不生成重复批次。

三类名单使用与人才管理完全相同的项目条件快照和判定服务。不合格与合格的按钮分开。Hi聊前预览项目招呼语、人数和预计点数。首次 Hi聊使用 51job 默认招呼；随后发送项目级文案。首次 Hi聊失败或点数不足者留在「待重试」，不入正式库。首次 Hi聊成功即标记「已联系」并入库；项目文案失败只重试文案，绝不再次发送首次招呼。

## 建议的数据与服务边界

| 边界 | 最小记录或接口 |
| --- | --- |
| 项目配置 | 条件、活跃度天数、条件版本、项目文案、每日计划时间与启用状态 |
| 扫描批次 | 项目、来源、账号、平台职位、业务日期、条件快照、起止时间、状态、三类人数 |
| 候选判定 | 平台候选人及记录 ID、资料来源、逐项证据、最终分类、是否完成详情读取 |
| 动作台账 | 项目＋平台候选人＋动作唯一键、确认人、请求时间、回执、失败原因、重试状态 |
| 平台适配器 | `ReadCatalog`、`ScanPending`、`ReadDetail`、`Reject`、`Hi`、`SendProjectMessage`；望远镜另有独立扫描入口 |

动作执行前须重新核验账号、职位、候选人和平台状态。候选人已执行过同一平台动作时直接展示既有回执；账号变化、条件版本变化或状态变化时停止该人并提示重新预览。

## 与当前代码的接入点和已知缺口

1. `scripts/51job_talent_management_import.js` 当前依赖 `TalentManagement`、`EhMenuPositions` 等页面内部组件，后台页只等待 6 秒；超时被统一描述成登录/加载问题。需要可区分的错误和真实页面验证。
2. `frontend/src/components/TalentManagementImportDialog.vue` 读取失败后保留旧 `jobs`；当前默认勾选四种状态，并直接提供「连续导入」。需改成仅待处理、扫描预览、确认后执行。
3. `recruitment_talent_management.go` 导入前只启用部分条件，读取条件错误被忽略；`KEEP_UNKNOWN` 仍可能入库。需统一判定结果并禁止待核实直接入正式库。
4. 同文件现有自动拒绝调用把原因标签传入应为 `projectID` 的参数，异步错误未汇报，详情读取固定第 1 页。应以逐人确认动作替换自动调用，并保存真实失败结果。
5. `recruitment_store.go` 的条件表尚无活跃度、项目文案、定时配置和批次/动作台账。现有每小时导入调度不能直接充当「每日生成待确认名单」。
6. 仓库尚无人才望远镜专用适配器；接入前需要在已登录的真实页面验证列表、详情、活跃度和平台操作入口，不能从通用搜索页面猜测选择器。

## 实施顺序与验收

1. **诊断与止错**：构建可重复的职位目录及导入故障回放；修复状态显示、旧目录误用、条件读取错误静默跳过和自动拒绝错误。没有真实回放前，不声称平台读取/操作已修复。
2. **共用规则**：条件迁移、活跃度、逐项三态判定、详情补读、条件版本及核心测试。
3. **人才管理批次**：仅待处理扫描、三类预览、分别确认、逐人动作台账、旧库重筛。
4. **人才望远镜批次**：专用适配器、项目定时与补跑、项目文案、Hi聊双阶段重试。

最低验收场景：本科门槛拦截已确认大专；学历缺失在详情仍未知时不入库、不拒绝；条件读取失败时整批停止；已推进状态完全跳过；浏览器读取失败不能用旧职位执行；同日补跑不重复名单或平台动作；Hi聊成功而项目文案失败时只重试文案；每人能查到真实平台回执或失败原因。
